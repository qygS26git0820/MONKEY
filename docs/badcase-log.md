## 一、阶段 1 期间的 Badcase

### BC-001 耗时被 `time.monotonic()` 量化成 16 ms 粒度

**现象**：轨迹里的耗时被量化成 0 / 15 / 16 ms，`ts_mono` 在相邻事件上**塌成同一个值**。而"耗时"是这个项目的一等观察目标之一，量化过的耗时数据不可用。

**根因**：`time.monotonic()` 在本机的分辨率实测为 16 ms（阶段 1 的 6 处计时调用都用了它）。这是 Windows 平台特性，不是代码写错——但设计时没有测过分辨率。

**优化**：新增 `harness/clock.py`：计时改用 `time.perf_counter()`，墙上时钟仍用 `time.time()`（用于跨日志对齐，不用于算时长）；把 6 处调用点全部迁移过去。这被明确记为**返工**而不是新增功能。

**验证**：本次重测（不引用旧结论）——`time.monotonic` 最小增量 0.016 s，`time.perf_counter` 最小增量 0.000000100 s，差 8 个数量级。

**残留**：无。

**证据**：`harness/clock.py:1-22`（docstring 里逐字记录了实测的分辨率）；`docs/stage1-retrospective.md` §2 表第 4 行、§5 表第 1 行、附录的时钟分辨率命令；提交 `3342dcf`（`harness/clock.py` 在其中）。

**优化前后对比**

| 维度 | 优化前 | 优化后 |
|---|---|---|
| 计时函数 | `time.monotonic()` | `time.perf_counter()`（`harness/clock.py`） |
| 本机分辨率 | 16 ms | 100 ns |
| 相邻事件 `ts_mono` | 塌成同一个值 | 可区分 |
| 几毫秒的调用 | 记成 0 或 16 | 记成实际值 |
| 调用点 | 散在 6 处 | 全部经 `clock.py` |

### BC-002 承诺了"去掉时间戳后逐字节一致"这个**不可保**的性质（D7）

**现象**：设计文档 §3、§8、§10、§12 **四处**承诺：重跑"去掉时间戳后轨迹逐字节一致"。这个性质**从未成立**。

**根因**：不是实现没做到，是**写下来的时候就错了**。两类抖动无法从源头消除：① 验证子进程**自报**的 unittest 运行时长（`Ran 2 tests in 0.000s` 里的数字）及其派生的 sha256；② 失败用例回溯里嵌的**工作区绝对路径**——而工作区路径含 `run_id`，由 `unittest` 自己打印，harness 控制不到。

**优化**：把表述改成"**动作序列一致**"，并把上面两条抖动来源写进文档；把现象本身**钉成断言**（`tests/test_determinism.py::test_failure_output_embeds_run_path`），这样将来换后端时这条会主动提醒重估，而不是被静默地归一化掉。

**验证**：该断言存在并在跑。阶段 2 切容器后端后，抖动如实发生：同一个 `read_file` 在 local 记 `workspace`、在 docker 记 `/workspace`——正是这条预测的形态。

**残留**：**跨后端失败输出的"可比性重估"没有做**。阶段 1 复盘 §7 第 2 条要求"切容器后端时重估"，阶段 2 结束时仍开着（阶段 2 复盘 §5 遗留第 2 条）。

**证据**：`docs/stage1-retrospective.md` §3.2；`docs/evidence/stage2-docker/05-replay-path-diff.txt`；`tests/test_determinism.py`；提交 `15d7ba4`（回填）。

**优化前后对比**

| 维度 | 优化前 | 优化后 |
|---|---|---|
| 文档承诺 | 逐字节一致（**不可保**） | 动作序列一致 |
| 抖动来源 | 未声明 | 两条明文写进文档 |
| 现象处置 | 被当成文档偏差 | 钉成断言，换后端时主动变红 |
| 对后端的依赖 | 未意识到 | 已知：失败输出里的路径随后端变 |

### BC-003 "文档-实现一致"是**未经核对**的结论（D10）

**现象**：上一轮我报告"文档与实现一致"。这个结论当时是**错的**：设计文档 §3 的交货物表 D6 行与 §4 第 4 点白纸黑字承诺了一个"哈希自证测试"，并点名 `tests/test_no_pollution.py`——**该文件当时不存在**。承诺存在，实现在。

**根因**：报告时没有逐条核对"文档承诺的测试是否存在"。测试当时全绿，因为它们不检查**自己被承诺过**。发现它的机制不是测试，是回填 D1–D9 时**逐节重读设计文档**撞上的。

**优化**：按"文档-实现一致"的标准，选择**补测试而不是删承诺**。新增 `tests/test_no_pollution.py`：断言跑完 4 组场景后 `harness/`、`configs/`、`tasks/` 的哈希清单逐条不变（`__pycache__` 除外），并单独断言 agent 的修复写进的是副本、不是任务模板。

**验证**：反证（一个从不失败的测试等于没有测试）——往 `tasks/toy-002/repo/settings.py` 注入一个字节，清单立刻检出该文件；还原后哈希复原。副产物留在 `tmp/settings.py.bak`（11 B）。

**残留**：**"文档承诺但代码里没有"这类偏差需要一条专门的检查，我想不出自动化的办法**（阶段 1 复盘 §4 第 2 点）。未解决，且这是本文件里我最没底的一条。

**证据**：`docs/stage1-retrospective.md` §4；`tests/test_no_pollution.py`；`tmp/settings.py.bak`（未入库）；提交 `3342dcf` / `15d7ba4`。

**优化前后对比**

| 维度 | 优化前 | 优化后 |
|---|---|---|
| 文档承诺的测试 | 不存在 | 存在并断言哈希清单 |
| "一致性"结论 | 未经核对就报告 | 有测试背书 |

## 二、阶段 2 期间的 Badcase

### BC-006 宿主环境变量整体泄漏给被观测命令（A1）

**现象**：`LocalExecutor` 把宿主环境**整体**交给被观测命令，于是 `MONKEY_DEEPSEEK_KEY` 对 agent 可见——一句 `printenv` 就把它送进 `trace.jsonl`、`blobs/` 和 `report.md`。观测数据里出现自己的凭据，就是**观测工具污染了观测对象**。

**根因**：子进程继承了全部宿主环境，而当时的"key 不出现"断言只测"我们自己的代码不写 key"，**测不到"被观测的 agent 主动读宿主环境"这条真正的通道**——测试绿，通道开着。

**优化**：`harness/env/local.py` 新增 `HIDDEN_ENV_PREFIX = "MONKEY_"` 与 `_child_env()`，把该前缀的宿主变量从子进程环境里过滤掉；显式传入的 `env` 不受限制（那条路径是调用方有意为之）。docker 后端本就不继承宿主环境（只透传显式 `-e`），这里补的是同一件事的宿主版本。

**验证**：补一条**负向测试**——让一个假 agent 主动 `printenv` / 读 `os.environ`，断言 key 仍然拿不到（原断言在旧实现下是假绿，必须先修通道它才有意义）。另有一次独立的凭据扫描：对 `docs/evidence/chaos-001/` 全目录搜 `sk-[A-Za-z0-9]|Bearer |Authorization|api_key|API_KEY|DEEPSEEK`，**0 命中**。

**残留**：两个后端的环境可见性口径仍需一致（审计 §7.5 标为"必修"，与 A1 同源）；`MONKEY_` 前缀**之外**的宿主变量仍然可见——这是设计取舍，不是漏洞。

**证据**：审计 A1（`docs/pre-llm-audit.md:16-22`）、§7.5、§8.8；`harness/env/local.py:19-33`；提交 `5b8c445`；`docs/stage2-retrospective.md` §3.3。

**优化前后对比**

| 维度 | 优化前 | 优化后 |
|---|---|---|
| 子进程环境 | 宿主环境整体继承 | 过滤掉 `MONKEY_` 前缀的变量 |
| `MONKEY_DEEPSEEK_KEY` | agent 一句 `printenv` 即得 | 拿不到 |
| 凭据进入轨迹的通道 | 开着 | 关闭（local 后端） |
| "key 不出现"断言 | **假绿**（只测我们自己的代码） | 有负向测试（agent 主动读也拿不到） |
| 两个后端 | 可见性口径不同 | 同一件事的两种答案（docker 本就不继承） |

### BC-007 多字节截断把交付文本**复制一遍**（A3）

**现象**：多字节输出在 8 KB–18 KB 区间触发截断时，交付给 agent 的文本**比原文还长**——`bytes_delivered` 18,031 > `bytes_total` 9,000，`elided_bytes` 为 **−9,000**，agent 读到 `[truncated -9000 bytes]` 这种乱码标记。而"截断"这个语义要求 `head_bytes + tail_bytes < total` 成立。被破坏的是**语义性质**，机械的重建性质反而全为 True。

**根因**：head/tail 的切点按**字符**（`head_chars=3000` / `tail_chars=3000`），保留量却**没有字节上限**。多字节内容下 3000 个字符可能是 9000 字节，头 9000 + 尾 9000 合起来覆盖甚至超过原文。触发条件是 `总字符数 ≤ head+tail` 且 `字节数 > threshold`。

**优化**：`prepare_stream` 给 head/tail 加**字节上限**（`kept_cap` / `head_cap` / 尾部的 `kept_cap - head_cap`），保证 `head_bytes + tail_bytes < total`；截断标记自身要占的字节先扣掉。

**验证**：审计的实测表（6 组数据，阈值 8192 B、head/tail 各 3000 字符）从"elided 为负"变成"elided ≥ 0"；修后把 `elided_bytes >= 0`、`bytes_delivered <= bytes_total` 立成断言（补进 `tests/test_truncate.py`，该文件此前是**假绿**：测试数据的最大规模永远进不了多字节重叠区）。混沌实验的两次实跑各只有一次截断，元数据均为正 elided：57,651 → 6,031（丢弃 51,651）、85,400 → 6,031（丢弃 79,400）。

**残留**：**截断参数仍是任意值**——`head_chars=3000` / `tail_chars=3000` / 阈值 8192 B 没有任何实验依据；换成别的值会不会让某个任务变得不可解，**没有测**。混沌实验的任务恰好落在"头尾都够不到、必须换成命令"的窗口里，**这个任务的难度有多大程度是截断参数造成的假象，不确定**。

**证据**：审计 A3（`docs/pre-llm-audit.md:16-22`）、§4.4、§8.3、实测表 `docs/pre-llm-audit.md:455-462`；`harness/trace.py:70-131`；提交 `5b8c445`；`docs/evidence/chaos-001/00-README.md` §二；`docs/chaos-retrospective.md` §4 第 5 条。

**优化前后对比**

| 维度 | 优化前 | 优化后 |
|---|---|---|
| 切点 | 按字符 | 仍按字符（不切断多字节字符） |
| 保留量上限 | **无** | 按字节（`kept_cap` 先扣掉标记） |
| `chars=3000` / 阈值 8192 时 | delivered 18,031 / total 9,000 / elided **−9,000** | elided ≥ 0，`bytes_delivered ≤ bytes_total` |

### BC-010 挂住的模型调用**无法被抢占**（A2）

**现象**：如果模型请求永不返回，主线程停在同步调用上——`timeout_step` 的检查在**调用返回之后**，`timeout_wall` 的检查在**下一轮循环开头**，两个都不会触发，**也没有任何抢占机制**，run 永久挂着。`trace-schema` #7 声称"阶段 2 起该标签涵盖模型挂住"：**标签的语义写对了，执行点不存在**。

**根因**：`loop.py` 是同步调用 `agent.next_action(state)`；`timeout_step` 只是一个"事后给慢步贴标签"的动作，不是"能掐断慢步的守卫"。而冻结的 `loop.py` **无法抢占一个同步调用**——修法只能在 HTTP 层做。

**优化**：由客户端自带超时，三层：① httpx 逐阶段 `Timeout(connect=5, read=45, write=10, pool=5)`；② httpcore 之下的真实 socket；③ **总时限 90 s 包住整次交换，做成线程级包装**。第 3 层不能写成"迭代 chunk 时查截止"——一个每 40 s 送 1 字节的滴流网关永远骗得过 `read` 超时；而若滴流发生在**响应头之前**，任何"响应头之后"的截止检查一次都跑不到。**A2 与 LLM 客户端同一个提交**（不允许"先装大脑，再补超时"）。

**验证**：用真实回环 TCP 服务器（`127.0.0.1` + 原始 socket）覆盖三种卡法——静默、正文滴流、响应头滴流——外加一条**反向对照**（正常服务器必须成功），否则"一切都超时"也会显绿。线程泄漏检查排到最前面、从干净基线起算，确认 0 个泄漏的 `llm-post` 线程。

**残留**：**三层超时在真实端点上一次都没触发过**（回环 ≠ 真实网关的 DNS / TLS 握手 / 排队 / 上游限流）；`read(45s) < total(90s)` 这条顺序不变量只在回环上验过。**不确定**它在那时的分工是否还成立。

**证据**：审计 A2、§5.2；`harness/llm/client.py`（314 行）；`tests/test_llm_client_timeouts.py`（442 行、16 项）；提交 `6c8d01a`；`docs/stage2-retrospective.md` §1.4(e)、§2 表。

**优化前后对比**

| 维度 | 优化前 | 优化后 |
|---|---|---|
| 模型不返回时 | run 永久挂住，只能外部 kill | 90 s 内以可识别失败返回 |
| `timeout_step` 的角色 | 事后贴标签 | 客户端超时 + 事后贴标签 |
| 滴流网关（每 40 s 1 字节） | 骗过任何"两次读之间的间隔" | 被总时限掐断 |
| 滴流发生在响应头之前 | 无任何代码能跑到 | 线程级包装仍有效 |
| 测试环境 | `httpx.MockTransport`（走不到 socket） | 真实回环 TCP + 反向对照 |
| 与客户端的关系 | 允许"先装大脑再补超时" | 同一提交，不允许中间状态 |

### BC-023 同一任务两次 run 的 token 差 30.9%，"预算耗尽"不等于"任务贵"

**现象**：同一个任务、同一个模型、同一份快照、同一个判据、**同样 13 步**，两次 run 的 token 差 **47,536（−30.9%）**：153,373 vs 105,837。更反直觉的是：第二次被截断丢弃的字节**更多**（79,400 > 51,651），但整体**更便宜**。

**根因**：差别不在"读了多少"，在"**多早**把大段文本放进上下文"。两次的截断事件**各只有一次**：第一次在 **step 3**（`read_file` 读 events 文件，一次读了**三份**文件），第二次在 **step 9**（模型自己的 `grep`，且前期先花两步做 `ls` 侦察）。而每一步都要重发**整段历史**，所以第一次那 6,031 字节从第 4 步起要被重发 **9 次**，第二次的从第 10 步起只重发 **3 次**——"早一步进上下文"的代价是复利。

**优化**：**无代码改动**。这是**观测结论**，它改变的是**解读口径**，不是代码：一条因 token 越限而死掉的轨迹，**不能直接读作**"这个任务超出了预算"。

**验证**：两次 trace 的每步输入序列（第一次 `978 1434 5210 8331 9443 12000 12393 12985 14799 17031 17631 18836 18907`；第二次 `978 1126 1643 3014 5434 6004 7886 8898 10766 13257 14157 14824 14895`）。

**残留**：n=2，**"先侦察、后分批读"是不是它做对的原因，无法证明**——这是**解释**而不是**归因**。另外这条与 BC-020 的"判据偏松"合起来暴露同一个问题：**"成功"与"花了多少"在本次是负相关的**（更贵的那次被判 `aborted`，更便宜的被判 `completed`）。

**证据**：`docs/chaos-retrospective.md` §2.1 / §2.2 / §3.2(3) / §3.2(4)；`docs/evidence/chaos-001/01-run1-token-budget-exceeded.trace.jsonl`、`06-run2-completed.trace.jsonl`；`docs/evidence/chaos-001/00-README.md` §二。

## 四、没有收录为 Badcase 的残差

以下条目来自 `docs/known-residues.md` 与三份复盘，它们**不是"实际发生过的缺陷"**，因此不单独立条；在这里列名与理由，避免"没收录"被误读成"忘了"。

| 编号 | 是什么 | 为什么不算 Badcase |
|---|---|---|
| R-001 | `UsageLedger` 的 token 未知量无法触发终止（粘性未知 + `exceeded()` 短路） | **刻意的设计取舍**："无法证明它超了，就不凭它终止"。凭未知量终止会造假阳性，比漏判更坏。从未在真实 run 上被触发过 |
| R-002 | 历史文档与证据仍命名已删除的成本面 | **历史产物**。它们在其所记录的时间点是准确的；改写等于伪造历史。是"文档腐烂"，不是缺陷 |
| R-003 | `phase1-sample-trace.jsonl` 的 `totals` 键名与现行 schema 不同 | 同上；该文件是**冻结样本**，逐字节不动是刻意的，且不影响合法性校验 |
| R-004 | 审计 §8.6 讨论的旧测试文件已删除 | 同上。所涉的边界覆盖**未被丢弃**（迁移到 `tests/test_token_budget.py`），仅作指针 |
| R-005 | 部分标签在 §1.3 表里仍标着"【建议新增】" | **纯观感**，无语义影响 |
| R-006 | `step` 是 agent 自计数的，靠"不重试"维持与主循环对齐 | **未激活的潜在风险**。当前"不重试"的取舍使自计数恰好等价；有测试（`test_the_self_counted_step_matches_the_loop_step`）钉住，加重试时先红。**一旦引入重试，它会变成真正的 Badcase** |
| R-007 | 工具 schema 与系统提示词的措辞是**未版本化**的实验条件 | **观察条件的缺口**，不是缺陷。它在阶段 3 **被实际踩到**：两次 chaos run 的任务描述、系统提示词、工具 schema **逐字相同，却没有任何哈希能证明这一点**（`config_hash` 覆盖不到它们）。要证明"两次实验条件相同"，只能逐条比对两条 trace 里的 `llm_request.messages`/`tools` 全文。**这条最接近 Badcase，但它的后果是"无法证明"而不是"证明错了"** |

## 五、一句话总结

这份台账共 **23 条**：**19 条已修或已处置、3 条仍开着**（BC-011 未修、BC-018 第 2 项仍开着、BC-019 登记不修），另有 **1 条从未被验证**（BC-022 的上限改判）。没有任何一条是"功能不工作"——全是**可信度的漏洞**：文档承诺了做不到的事、测试是假绿、标签名与实际含义不符、观测工具污染观测对象、判据比它声称的松、实验条件无法证明相同。这与这个项目的目标（证明观测是可信的）是同一件事，所以它们值得单独成册。
