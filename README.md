# MONKEY

> 一个能自主修 bug 的 AI Agent，行为可记录、可回放、可归因。

## 一、这是什么

MONKEY 是一个 AI Agent。给它一个任务和一份代码，它会自己读文件、改代码、跑命令，
直到把问题解决——或者自己判断解决不了。

它的每一步决策都来自 DeepSeek：该看哪个文件、该改哪一行、下一步做什么，由模型自己定，
不是我们写死的流程。

它在一个隔离的容器里干活，碰不到外面。**而它做的每一件事都被记下来**：看过哪些文件、
发过什么命令、命令回了什么、模型当时手里握着哪些信息。这些记录事后可以回放，逐条核对。

它最在意的不是"能不能修好"，而是"**能不能说清楚它是怎么修的**"。
所以它的重点在"行为可观测"，不在"提供功能"——这不是一个拿来用的工具，
是一个拿来观察的对象。

它有一条贯穿始终的习惯：**每个结论都要指得出证据**。指不出证据的结论，
就写成"不确定"。

## 二、项目做了什么（四个阶段）

| 阶段 | 做了什么 | 状态 |
|---|---|---|
| 阶段 0 | 环境审计——先把"我们究竟能看见什么、看不见什么"摸清楚 | 已完成 |
| 阶段 1 | 骨架搭建——把"记录 → 回放 → 核对"这条链子做通 | 已完成 |
| 阶段 2 | 接入真实模型（DeepSeek Flash，配置记作 `deepseek-flash`），让它第一次真的动手修 bug | 已完成 |
| 阶段 3 | 混沌实验——在真实的故障现场让它做诊断，看它的行为边界在哪里 | 已完成 |

阶段 2 和 3 各跑过**真实付费调用**，花费与步骤都留了档。

## 三、项目结构

```
harness/    Agent 本身的代码——它怎么看、怎么想、怎么动手、怎么记录
tasks/      任务定义——每个任务一份说明 + 一份判据（"怎么算做对了"）
configs/    配置——步数上限、超时、记录方式、用哪个模型
docs/       文档——设计、复盘、审计、台账、证据
```

另有 `tests/`（对 Agent 自己的自检）与 `runs/`（每次运行的产物，不进版本库）。

## 四、关键文档

- `docs/trace-schema.md` —— **轨迹契约**。一次运行里该记哪些事、每个字段什么意思，
  都在这里。它是整个项目的接口约定，改动要留痕。
- `docs/badcase-log.md` —— **23 条 Badcase 台账**。按阶段归档，每条写清现象、根因、
  怎么处置的、还剩什么没解决，并附"优化前后"对照。
- `docs/chaos-retrospective.md` —— **混沌实验复盘**。实验设计、两次运行的差异、
  它的行为边界、以及我自己最不确定的地方。
- 此外还有设计文档、三份阶段复盘、装大脑前的安全审计与残差台账，都在 `docs/` 下。

## 五、项目状态

- **阶段 0–3 全部完成**，22 条提交。
- **自检**：146 项通过（其中 6 项按条件跳过）。
- **已知残留**：还有 3 条问题**没有修**，但都登记在册，写明了"为什么不修"——
  这个项目认为"记下来"比"顺手改掉"更重要。
- **证据**：每次真实运行的关键产物都被逐字节复制进 `docs/evidence/`，
  可以在离线、零成本的前提下复核。

## 六、说在最后

这个项目里，**"成功"永远带着前缀**：在什么条件下成功、几次里成功、判据有多严、
有多少是我没能验证的。翻一翻 `docs/badcase-log.md` 就知道——23 条里没有一条是
"功能坏了"，全是"我们差点信了自己不该信的东西"。
